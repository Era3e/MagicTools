# P03/P05：可独立运行的镜像与不可变发布

用户已授权持续实现、独立验收及检查通过后直接合并。本批基于已合并 #71 的 main 531e82a，补齐 P03/P05，不以本地源码运行替代真实镜像验证。

## 方案选择

采用 pnpm deploy 生成独立生产运行目录，携带应用依赖、工作区共享包、dist、迁移和必要资源。手工复制根 node_modules 会缺少包级链接；复制整个仓库会带入开发依赖和配置，均不作为交付方案。

运行镜像采用 Node 22，主机与既有 quality 继续验证 Node 20 兼容性；实际容器单独验证 Node 22 行为。Web 保留 Nginx 运行形式。所有镜像记录源码 revision；发布使用 SHA 标签和 registry digest，不以 latest 作为部署依据。

## 运行契约

1. 所有9个Node服务镜像包含独立生产依赖；八个业务服务包含迁移，Gateway包含 infra/ports.yaml，Designer包含运行时预览需要的esbuild、React和@mt/ui。
2. 构建上下文排除 .env*、.qa、Git元数据、日志和临时制品；生产秘密通过运行环境提供。
3. 存活检查与就绪检查分开。业务服务只有在迁移成功后才监听/启动调度器；readiness 每次确认数据库可访问，断连返回503。初始化失败进程非零退出。
4. Compose修正初始化SQL的相对挂载，PostgreSQL使用TCP健康检查，业务服务依赖数据库健康，网关及Web提供自身就绪探针。入口、端口、服务清单仍来自现有端口映射。
5. 新应用模板采用同一运行契约，避免生成旧的缺依赖镜像。

## 发布与部署契约

1. 制品清单包含固定源码SHA、目标平台、17个服务的镜像引用及实际registry digest。digest由推送后的registry结果读取并核验，不能用本地image ID冒充。
2. 部署使用清单生成的digest固定配置，记录清单校验和、配置版本、就绪结果与上一个成功制品清单。
3. 发布参数与.env秘密配置分开，部署脚本不覆盖已有.env；检查本地/SSH子进程退出码，等待就绪后才写成功回执。
4. 拉取、迁移、就绪或镜像引用失败时返回非零并写失败回执；保留上次成功制品，提供显式回退路径。应用回退不自动逆向数据库迁移，恢复数据库由备份方案负责。
5. PR的smoke检查加入真实镜像冷启动验证；保留quality/smoke/e2e三个required check名称。main发布有配置时使用不可变清单，没有真实registry配置时明确不发布。

## 实施与验收

按行为RED→GREEN实现：启动与readiness、独立镜像、Compose冷启动、digest清单、部署失败与回退。测试智能体与实现者分开。

- 从干净构建上下文构建全部17镜像；运行时不挂载源码或宿主node_modules。
- 独立Compose project/network/全新卷，数据库不占用宿主5432；验证八库迁移、17服务就绪、Web深链及静态文件、代表性CRUD和Designer预览。
- 重启服务验证持久数据；错误密码、迁移失败、数据库断连和不存在的镜像必须导致就绪/部署失败。
- 使用本轮一次性registry验证两版SHA/digest；移动标签不改变已固定部署；回退指向上次成功清单；已有秘密配置保持原样。
- 本地门禁、独立验收、容器回归与CI通过后自动合并。测试部署、生产上线和真实外部模型效果分别记录。
