# Manager 需求基础与候选导入

适用范围：2026-09-11 起新增的需求修订、候选导入与能力基线。自动执行队列、批准修订及自动合并不属于本次功能。

## 使用流程

1. 打开 Manager 的管理后台「需求管理」，点击「导入候选」。
2. 选择或粘贴 `magictools-requirement-candidates/0.1` JSON，单批最多 90 KiB、200 条。
3. 点击「预览候选」，查看新增、重复、冲突和每条来源证据；预览只保存候选批次。
4. 选择需要记录的条目，点击「确认导入选中项」。能力基线与规划需求分别保存。
5. 「查看能力基线」展示源码观察、核验缺口和源提交；规划进入待分析需求，可在详情查看验收条件及代码证据。

能力基线不代表已验收或已部署，不计入需求完成率。规划默认人工开发，确认导入不会授权自动开发，也不会把需求标记完成。

## 来源与重复处理

- 输入必须标记 `review_status=unreviewed`、`automation_eligible=false`，每条证据指向同一 GitHub 仓库、提交、文件与行号。仓库身份不区分大小写，证据 URL 同步归一化；文件路径仍区分大小写。
- 文件选择限制原始文件最多 90 KiB；API 的 90 KiB 限制针对解析后的 JSON 内容（不含排版空白），传输层仍受应用请求体上限约束。
- 校验覆盖来源结构与一致性；服务端不远程读取源码，因此不将链接结构正确宣称为代码内容已核验。
- 候选编号是稳定外部键，不应在每次导出时重新编号。相同仓库与编号的相同内容复用既有目标。
- 同编号不同内容显示冲突，不覆盖已保存或人工编辑的内容。应先人工比较，再决定用新编号表示新需求还是在既有需求中编辑。
- 同一批次确认一次；重复提交相同选择返回同一结果。部分确认后点击「继续预览未选候选」，系统从剩余项创建新批次，不改变原确认回执。
- 交叠批次以事务与按固定顺序获取的业务键锁去重；一项冲突导致本批全部回滚。
- 候选的前置编号保留为引用，当前不自动解析为已完成依赖；排期时仍需核验。

## 需求状态与修订

普通状态迁移：待分析→设计中或待开发；设计中可退回待分析或进入待开发；待开发可退回设计或进入开发；开发可退回待开发或进入测试；测试可退回开发或进入验收；验收可退回测试或标记完成；已完成是终态。

PR 状态是外部事实，可补齐遗漏的中间事件，但不能把已验收/已完成回退，也不能自动宣布产品完成。同状态 PR 事件不会增加修订或追加时间线。

PATCH 将字段和状态在同一事务修改，返回 `revision`。新客户端提交 `expectedRevision`，过期版本返回 409；旧客户端暂可省略该字段，但无法获得基于旧页面快照的冲突保护。事务行锁仍保证字段合并与时间线不丢失。

关联表单独立保存草稿及其基准修订。普通状态/优先级刷新保留草稿；服务器关联改变时保留旧基准并提示冲突，显式重新载入后再编辑，避免重试覆盖他人修改。

`revision` 是并发版本。P08 新增独立的内容版本与审批记录，见 [需求内容修订与审批](manager-content-approval.md)；导入与旧客户端写入同样由数据库触发器记录内容快照。

## API

| 方法 | 路径（前缀 `/api/manager`） | 行为 |
|---|---|---|
| POST | `/import-batches/preview` | 验证候选包，保存或复用批次，返回处理预览 |
| GET | `/import-batches/:id` | 获取批次、处理分类及确认结果 |
| POST | `/import-batches/:id/confirm` | 提交 expectedRevision 和 candidateIds，事务确认 |
| POST | `/import-batches/:id/remaining-preview` | 为尚未导入的候选创建新预览，继续部分导入 |
| GET | `/capabilities` | 查询独立保存的能力基线 |
| PATCH | `/requirements/:id` | 提交白名单字段与可选 expectedRevision，原子更新 |

当前接口沿用已有 Gateway 的访问边界，不新增独立身份或细粒度角色体系；对外启用前仍需完成生产认证与权限配置。

## 开发验证

`pnpm qa:gate` 是本地与 CI quality 的共同入口，包含 lint、build/test、coverage、基础设施、文档、设计检查，以及 Manager 关键数据库契约测试。

CI 复用原有 pgvector PostgreSQL 服务，在独立的 mt_manager_test 库执行新增契约。基础设施测试严格解析全部 workflow YAML，重复字段会在提交前被阻断。

配置 `MANAGER_TEST_DATABASE_URL` 指向名称为 `mt_*test` 的专用 PostgreSQL 测试库，例如开发机 PostgreSQL 的 `mt_manager_test`。集成配置会读取仓库根 `.env`；不能把全局 DATABASE_URL 指向某个业务库用于全仓测试。

单独运行 `pnpm test:manager:integration`；没有有效配置或数据库不可用即失败，不跳过。此专用套件覆盖原子修改、状态约束、并发版本、PR 幂等、导入预览、重复和交叠确认、冲突回滚、来源与自动化标记校验。

既有其他子项目的数据库测试仍沿用原有模式，本次没有把它们全部改为强制执行；桩测试也不代表真实模型效果。
